程序只需要写出调用的函数名，最后；编译器却必须把它变成机器指令，而机器指令最终需要知d道函数在内存中的位置。这个名字如何找到定义、地址何时确定、共享库又如何在不同进程中复用？这些问题都属于“链接”。

本文以 Linux x86-64 和 ELF 为例，从一个由多个 C 文件组成的小程序开始，沿着“编译—链接—加载—执行”的路径逐层展开。不同操作系统的文件格式和细节会有差异，但符号解析、地址确定和代码复用这些核心问题是相通的。

## 一个程序是如何运行起来的

先看一个最小的多文件程序。`main.c` 负责调用求和函数：

~~~c
/* main.c */
int sum(int *values, int count);

int main(void) {
    int values[] = {1, 2, 3, 4};
    return sum(values, 4);
}
~~~

`sum.c` 提供函数定义：

~~~c
/* sum.c */
int sum(int *values, int count) {
    int result = 0;
    for (int i = 0; i < count; ++i) {
        result += values[i];
    }
    return result;
}
~~~

程序从源代码到运行，大致经历下面几个阶段：

~~~mermaid
flowchart LR
    A["main.c / sum.c"] --> B["预处理"]
    B --> C["编译为汇编"]
    C --> D["汇编为 .o"]
    D --> E["静态链接器 ld"]
    E --> F["ELF 可执行文件"]
    F --> G["execve / 内核加载"]
    G --> H["动态链接器加载共享库并完成重定位"]
    H --> I["_start → 运行库初始化 → main"]
~~~

平时使用的 `gcc` 不只是 C 编译器，也是一个**编译器驱动程序**：它会按需调用预处理器、编译器、汇编器和链接器。可以把各阶段显式拆开观察：

~~~sh
gcc -E main.c -o main.i       # 预处理
gcc -S main.i -o main.s       # 编译为汇编
gcc -c main.c -o main.o       # 编译并汇编，生成可重定位目标文件
gcc -c sum.c -o sum.o
gcc -o app main.o sum.o       # 链接
./app
~~~

`main.o` 中已经有 `main` 的机器指令，但它调用的 `sum` 尚未定义在这个文件里；`sum.o` 则提供了定义。链接器把它们组合起来，形成可执行文件。运行 `./app` 时，shell 请求内核创建进程并执行该文件。内核建立进程的虚拟地址空间、映射程序所需的内容，然后把控制交给程序入口；入口代码完成运行库初始化后，才会调用我们熟悉的 `main`。

这里先记住两个角色：**链接器处理目标文件和符号，加载器负责让程序进入进程并开始执行**。在动态链接的程序中，动态链接器也会在 `main` 运行前参与工作。

## 什么是链接

**链接（linking）**就是把多个代码和数据片段收集起来，解析它们之间的引用关系，并组成可执行文件或共享库的过程。比如 `main.o` 对 `sum` 有一个引用，链接器需要找到 `sum` 的定义，并让这条调用指向正确的位置。

链接主要要解决两类问题：

1. **符号解析（symbol resolution）**：确定每个外部符号引用对应哪个定义。符号通常代表函数、全局变量或静态变量。
2. **重定位（relocation）**：确定代码和数据最终放在哪里，并修补指令或数据中的地址，使引用能够到达目标。

链接不一定只发生在生成可执行文件时。它可能分布在不同阶段：

| 时机 | 主要工作 | 常见例子 |
| --- | --- | --- |
| 编译时 | 将独立的目标文件合并，尽可能确定符号和地址 | `main.o` 与 `sum.o` 链接 |
| 加载时 | 程序启动时载入共享库，并解析必要的引用 | 可执行文件依赖 `libc.so` |
| 运行时 | 程序运行后按需载入库或解析函数 | `dlopen`、延迟绑定 |

“静态”与“动态”说的是链接工作何时完成、库的代码是否被复制进最终程序等区别，不是说静态链接不需要加载器。无论哪种方式，操作系统都要创建进程并映射程序；动态链接只是把一部分符号解析和重定位留给运行时。

## 目标文件的结构

编译器和汇编器通常先生成**可重定位目标文件**。它已经包含机器码，但还没有确定所有最终地址，也可能保留对外部函数和变量的引用。ELF 将这些内容组织在不同的节（section）中：

| ELF 节 | 用途 |
| --- | --- |
| `.text` | 程序的机器指令 |
| `.rodata` | 字符串常量等只读数据 |
| `.data` | 已初始化的全局变量和静态变量 |
| `.bss` | 未初始化或显式初始化为零的全局变量和静态变量；文件中通常只记录所需大小，加载后由系统置零 |
| `.symtab` | 编译和链接所需的符号表 |
| `.strtab` | 符号名称等字符串 |
| `.rel.text` / `.rela.text` | `.text` 中需要链接器修补的位置及其计算信息 |
| `.dynamic`、`.dynsym`、`.dynstr` | 动态链接所需的依赖、符号和字符串信息 |

一个 ELF 文件还会有 ELF 头和节头部表。ELF 头描述文件类型、目标机器等信息；节头部表记录各节的位置、大小和属性。链接时常讨论“节”，加载时则更多看程序头部表描述的 **segment（段）**，例如可读可执行的代码段和可读可写的数据段。一个段可以覆盖一个或多个节；节服务于链接和组织，段服务于装载映射。

常见的目标文件有三种：

- **可重定位目标文件**（如 `.o`）：可以和其他目标文件继续链接。
- **可执行目标文件**：可被加载并运行；若依赖共享库，仍需动态链接器参与。
- **共享目标文件**（如 Linux 的 `.so`）：可以在启动时或运行时加载，并与进程中的其他目标文件链接。

可用 GNU binutils 初步查看这些结构：

~~~sh
readelf -h main.o       # ELF 头
readelf -S main.o       # 节表
readelf -s main.o       # 符号表
readelf -r main.o       # 重定位条目
objdump -d main.o       # 反汇编
~~~

## 符号解析和重定位

### 符号表：记录“谁定义了什么”

目标文件里的符号表可以看成链接器的索引。每个符号条目会关联名称、类型、绑定属性、所在节和节内偏移等信息。以 `main.o` 为例，`main` 是本文件定义的函数，而 `sum` 是一个尚待解析的外部符号。`sum.o` 中则有 `sum` 的定义。链接器通过名称和符号属性把两边对应起来。

C 语言中的 `static` 也会影响链接器可见的范围：文件作用域的 `static` 函数或变量具有**内部链接**，只在当前源文件对应的模块内可见；普通的文件作用域函数和全局变量通常具有**外部链接**，可供其他目标文件引用。函数内部的自动局部变量一般位于栈中，并不作为可供其他文件解析的全局符号。

重复定义也需要规则。传统 ELF 链接语境中，强符号通常是函数和已初始化的全局变量，弱符号常由带 `weak` 属性的定义产生。一般规则是：多个强定义会导致链接错误；一个强定义优先于弱定义；多个弱定义中通常选取其中一个。依赖这些规则解决业务逻辑冲突很危险，尤其是不同文件里类型或大小不一致的全局变量，可能造成静默的数据破坏。尽量让全局定义唯一，并用 `static` 限制不需要导出的名字。

静态库（`.a`）是由多个可重定位目标文件组成的归档。链接器通常按命令行顺序扫描库，只提取能解决当前未定义符号的成员。因此，使用该库的目标文件通常要放在库之前：

~~~sh
gcc -o app main.o ./libvector.a
~~~

如果把 `./libvector.a` 放在 `main.o` 之前，某些链接器在扫描到库时还不知道后面会需要哪些符号，因而可能不会提取对应成员，最终报 `undefined reference`。这个顺序问题针对静态库尤其常见。

### 重定位：把引用改成可用的地址

汇编器生成 `main.o` 时，并不知道 `sum` 最终会被放到哪里。因此，它会在需要修补的位置留下占位内容，并在重定位表中记录：

- 哪个节里的哪个偏移需要修改；
- 要引用哪个符号；
- 使用哪种重定位类型；
- 计算时使用的附加值（addend）。

链接器布局各个节、确定符号地址后，按重定位类型计算新值并写回对应位置。常见的两种思路是：

- **绝对地址**：把目标符号地址（以及 addend）写入引用位置，概念上可写为 `S + A`。
- **PC 相对地址**：写入目标相对当前位置的位移，概念上可写为 `S + A - P`。

这里 `S` 是目标符号地址，`A` 是附加值，`P` 是需要修补的位置。以 x86-64 的 `call rel32` 为例，指令使用相对位移而不是把完整目标地址嵌在指令里。CPU 会以指令中位移字段之后的位置为基准，因此重定位 addend 可能需要补偿字段长度。这样，链接器填入正确的位移后，调用指令就能到达 `sum`。

重定位不是简单地“把符号名替换成地址”：链接器必须理解目标机器指令、寻址方式和重定位类型。也因此，目标文件里通常既有机器码，也有帮助工具链继续处理它的元数据。

## 动态链接的基本思想

如果把常用库的所有机器码都复制进每个可执行文件，会造成磁盘和内存浪费；库更新后，应用还可能需要重新链接。**共享库**把库代码和数据单独保存在 `.so` 文件中，程序只记录依赖关系以及运行时完成链接所需的信息。

共享库带来两层“共享”：

1. 文件系统里多个程序可以依赖同一个 `.so` 文件。
2. 运行时，多个进程可以映射同一份只读代码页；每个进程仍有自己的可写数据。

在 Linux 上构建一个简单共享库，可以这样做：

~~~c
/* vector.h */
#ifndef VECTOR_H
#define VECTOR_H
void addvec(const int *x, const int *y, int *out, int n);
#endif
~~~

~~~c
/* addvec.c */
#include "vector.h"

void addvec(const int *x, const int *y, int *out, int n) {
    for (int i = 0; i < n; ++i) {
        out[i] = x[i] + y[i];
    }
}
~~~

~~~c
/* main.c */
#include <stdio.h>
#include "vector.h"

int main(void) {
    int x[] = {1, 2}, y[] = {3, 4}, out[2];
    addvec(x, y, out, 2);
    printf("%d %d\n", out[0], out[1]);
    return 0;
}
~~~

下面的命令在 Linux/ELF 环境下生成并链接共享库：

~~~sh
gcc -fPIC -shared -o libvector.so addvec.c
gcc -o app main.c -L. -lvector -Wl,-rpath,'$ORIGIN'
./app
~~~

`-fPIC` 让编译器生成适合放在任意地址的代码；`-shared` 生成共享目标文件；`-L.` 和 `-lvector` 指定链接时查找当前目录中的 `libvector.so`；示例里的运行路径设置让动态链接器可以从可执行文件所在目录找到它。实际发布软件时，库通常安装到系统库目录或由运行环境配置搜索路径。

链接这一步**不会把 `libvector.so` 的代码复制进 `app`**。链接器会记录动态依赖（例如 `DT_NEEDED`），并留下动态符号表和重定位信息。运行 `app` 时，典型流程是：

1. shell 请求内核执行程序；内核映射可执行文件需要的段。
2. 若 ELF 声明了动态解释器，内核也会启动该动态链接器（Linux 上常见为 `ld-linux`）。
3. 动态链接器查找并映射依赖的共享库，解析符号，并完成必要的重定位。
4. 链接准备好后，控制进入程序入口；运行库完成初始化，最终调用 `main`。

在整个过程中，文件往往通过虚拟内存映射进入进程；页面会在实际访问时载入，而不是简单地把整个文件一次性复制到物理内存。

程序也可以在运行过程中主动加载库，例如插件系统、图像编解码器或可选后端。这时可以使用 `dlopen`、`dlsym`、`dlclose`。沿用上面的 `libvector.so`，新建一个不在编译时链接它的 `plugin.c`：

~~~c
#include <dlfcn.h>
#include <stdio.h>

typedef void (*addvec_fn)(const int *, const int *, int *, int);

int main(void) {
    void *handle = dlopen("./libvector.so", RTLD_NOW);
    if (handle == NULL) {
        fprintf(stderr, "%s\n", dlerror());
        return 1;
    }

    dlerror(); /* 清除此前可能存在的错误 */
    addvec_fn addvec = (addvec_fn)dlsym(handle, "addvec");
    const char *error = dlerror();
    if (error != NULL) {
        fprintf(stderr, "%s\n", error);
        dlclose(handle);
        return 1;
    }

    int x[] = {1, 2}, y[] = {3, 4}, out[2];
    addvec(x, y, out, 2);
    printf("%d %d\n", out[0], out[1]);
    dlclose(handle);
    return 0;
}
~~~

~~~sh
gcc -o plugin plugin.c -ldl
./plugin                 # 输出：4 6
~~~

`RTLD_NOW` 要求加载时解析所需符号；`RTLD_LAZY` 则允许部分函数引用延迟到第一次调用时解析。使用动态加载时，句柄和函数指针的有效期受库的加载状态约束，卸载后不能继续调用其中的代码。

## 位置无关代码——GOT和PLT的运用

共享库可以被映射到不同进程地址空间中的不同位置。若机器指令里写死了某个全局变量或函数的绝对地址，加载器就必须修改共享库的代码页。这样既增加启动时的工作，也会妨碍代码页在进程间共享。

**位置无关代码（Position-Independent Code，PIC）**通过相对寻址和间接访问，避免把运行时绝对地址直接写进共享代码。GCC 通常使用 `-fPIC` 生成共享库所需的 PIC。

### GOT：从固定相对位置取得运行时地址

**全局偏移量表（Global Offset Table，GOT）**是模块自己的数据表，其中的条目保存需要在运行时确定的全局数据或函数地址。代码可以用相对于指令指针（x86-64 的 RIP）的固定偏移找到 GOT 条目，再从条目里读取实际地址。

概念上，对外部全局变量的访问类似这样：

~~~asm
mov global_value@GOTPCREL(%rip), %rax
mov (%rax), %edx
~~~

第一条指令通过 PC 相对寻址找到 GOT 条目，第二条再访问变量本身。库无论被映射到哪里，代码和 GOT 之间的相对距离仍可保持不变；动态链接器只需在运行时把正确的绝对地址写入 GOT 数据项，而不必改动共享代码。

### PLT：通过跳板调用外部函数

**过程链接表（Procedure Linkage Table，PLT）**为外部函数调用提供代码跳板，通常与 GOT 配合。调用方跳到本模块固定位置的 PLT 项，由它间接跳转到 GOT 中的函数地址。这样，调用指令不必知道共享库函数最终被映射到哪里。

在支持延迟绑定的配置下，某个函数第一次被调用时，GOT 对应项还指向 PLT 中的解析路径。动态链接器据此找到真正的函数地址，将其写入 GOT；后续调用经过同一个 PLT 项时，就可以直接间接跳到已解析的函数。

~~~mermaid
sequenceDiagram
    participant C as 调用方代码
    participant P as PLT 项
    participant G as GOT 项
    participant D as 动态链接器
    participant F as 共享库函数
    C->>P: call 函数对应的 PLT 项
    P->>G: 第一次调用，读取尚未解析的入口
    G->>D: 进入解析流程
    D->>F: 查找符号并取得运行时地址
    D->>G: 将真实地址写回 GOT
    D->>F: 转交控制
    C->>P: 后续再次调用
    P->>G: 读取已更新的地址
    G->>F: 直接跳转到函数
~~~

延迟绑定避免程序启动时解析那些永远不会调用的库函数，但第一次调用会多出解析开销。需要启动时立即解析时，可以使用 `RTLD_NOW` 或链接器相关选项；具体绑定策略也会受工具链和运行环境配置影响。无论采用哪种策略，GOT/PLT 的共同目标都是：把可变的运行时地址放在数据项中，通过稳定的代码路径访问它。

## 小结

从源文件到运行中的程序，可以把链接理解成逐步回答三个问题：

1. **符号在哪里定义？** 符号表与符号解析把引用关联到定义。
2. **目标最终位于哪里？** 重定位根据节布局和目标机器的寻址方式修补引用。
3. **共享库的地址何时确定？** 动态链接器可以在程序启动时完成，也可以在运行时按需完成；PIC、GOT 和 PLT 则让代码不依赖共享库的固定装载地址。

遇到链接问题时，可以按层次排查：先确认目标文件和库是否参与链接，再检查符号是否定义、可见性与库顺序是否正确；如果程序能链接但启动失败，再检查动态依赖和库搜索路径；若问题与地址或调用行为有关，进一步查看 ELF 的符号表、重定位表和反汇编。

~~~sh
nm -u main.o                 # 查看尚未定义的符号
readelf -r main.o            # 查看重定位条目
readelf -d app               # 查看动态依赖和动态链接信息
ldd ./app                    # 查看运行时共享库依赖
objdump -d app               # 查看反汇编
~~~

掌握这些基础后，`undefined reference`、库顺序错误、运行时找不到 `.so`、共享库函数首次调用的额外跳转，都不再是彼此无关的现象，而是同一条“符号解析与地址绑定”链路在不同阶段的表现。
